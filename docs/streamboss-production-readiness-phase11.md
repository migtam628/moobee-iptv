## First run: bounded loopback probe (Stream VPS only)

The API must already be listening at `127.0.0.1:18000` in the
`moobee-iptv-stage` container, with staging login generated by
`scripts/prepare_streamboss_stage.py`. This is a **new test container**;
it does not restart the staging server.

```bash
cd /opt/moobee-iptv-gateway-stage
git pull --ff-only origin staging/streamboss-tailnet-e2e-20261012

docker run --rm \
  --network host --read-only \
  --cap-drop ALL --security-opt no-new-privileges \
  -e MOOBEE_STAGE_READINESS_ACK=isolated \
  -e PYTHONDONTWRITEBYTECODE=1 \
  -v "$PWD/runtime/data/stage-access.txt:/stage-access.txt:ro" \
  -v "$PWD/scripts/staging_gateway_readiness.py:/readiness.py:ro" \
  --entrypoint python moobee-iptv-gateway-stage:20261012 \
  /readiness.py --max-viewers 3 --rounds 2
```

No `STREAM_SERVICE_API_KEY` is supplied to this test client. It
reads the temporary Xtream password from a read-only container mount and
never prints any credential, playlist URL, exception string, or response body.
It checks 401 on a bad password and for 1, 2 and 3 concurrent simulated
viewers fetches movie/episode master + media playlists + exactly one MPEG-TS
segment. It prints latency medians and p95, failures and segment-byte totals.
There are at most **12 sessions and 36 media requests**, all loopback to
the staging gateway, each one triggered by bounded test tasks. This is only
a first-stage functional load probe, **not** a production capacity estimate.

## Manual playback smoke in StreamBoss

Keep the existing Mac SSH tunnel open, use only the isolated staging Xtream
source, and check:
1. Movie and episode each start reliably from a fresh app launch.
2. Pause and resume without unexpected errors.
3. Seek to the middle and back; check that playback resumes with video/audio.
4. Observe startup delay, any stalls, and whether the app displays a media
   error (redact URLs/passwords from screenshots or logs).
5. Test two StreamBoss sessions only if a second device independently has a
   private staging tunnel; the scripted 3-viewer probe is not a realistic
   concurrent video streaming test.

## Important production blockers before merge/deployment

1. **Credentials in URL paths.** The gateway rewrites HLS paths containing
   Xtream username/password. They must never appear in access/error logs,
   analytics, crash reports or telemetry. Review Caddy and framework logs,
   client errors, redirects, proxies and retention policies. Move toward
   time-bounded session tokens before broad deployment.
2. **Connection limits not enforced.** Current player_api returns
   `max_connections=1` but does not enforce concurrent playback or track
   active connections. The staging probe intentionally uses one fake login,
   not multiple real subscribers.
3. **Per-segment upstream resolver and buffering.** Each HLS request fetches
   a fresh signed playback path; an HLS segment is buffered in memory up to
   16 MiB rather than streamed to the client. Concurrent viewers can amplify
   API/database load and memory consumption. Benchmark, optimize, and add
   robust back-pressure and concurrency controls.
4. **Production container path.** Host-network Tailscale connectivity was
   verified, and the existing production IPTV Docker bridge can reach the
   HTTPS health endpoint. The composed production path with this merged
   branch and all runtime flags still needs isolated bridge-mode testing.
5. **DNS/egress pinning.** Exact trusted HTTPS hostname and TLS verification
   are present, but resolved IP is not cryptographically pinned to Tailscale
   CGNAT. Verify actual egress policy and expected resolved tailnet IP.
6. **Timeout and error behavior.** Upstream HTTP timeouts could surface as
   a playback error at scale. Need testing of Stream restart, revoked service
   key, gateway restart, unavailable/expired upstream signature, and valid
   slow viewers, with fail-closed behavior.
7. **Subscriber expiry.** Current user storage verifies password and
   disabled flag; it has no real expiration policy or enforced view limit.
   Do not advertise enforcement based on a static account_info field.
8. **Capacity and observability.** A three-client one-segment probe is not
   evidence of maximum simultaneous viewers. Establish baseline bandwidth,
   CPU, RAM, FD counts, segment latency, error rate, stability under
   realistic full-duration video sessions on 2-vCPU Stream VPS.

## Proposed production release gates

- CI green on combined commit and separate code/security review.
- Two real titles played to completion in StreamBoss, including seek/resume.
- Revocation succeeds while a client is connected.
- No service key, signed paths, or subscriber passwords in collected logs.
- Benchmarks recorded at 1/2/3 users, then representative longer soak.
- Production IPTV data backup successfully taken **before** any write/deploy;
  use `bash scripts/backup-db.sh` from its production checkout.
- Rollback verified in a non-production environment; keep both flags
  `MOOBEE_STREAM_ENABLED` and `MOOBEE_STREAM_PLAYBACK_ENABLED` false
  by default. A production rollback that changes env requires controlled
  API recreation and should not be improvised.
- Explicit approval before changing production `162.35.165.218`
  (always use `compose.yaml` + `compose.hostnet.yaml` together).

## Boundaries

Never run load test against live `tv.moobee.lol` without approval.
No changes to live Caddy, DNS, Tailscale, firewall, subscriber database,
or StreamBoss production source in this phase.
